# v0.11.0 GitOps Airflow Release Cutover Plan

> **Historical design record.** Commands below are preserved as implementation evidence and are not current runbooks. Use [Module-size debt ratchet](../../module-size-ratchet.md) for the supported exact-SHA command.

**Goal:** Promote the GitOps and Airflow control-plane stack into a guarded
`v0.11.0` release candidate without losing the already released `v0.10.0`
route certification baseline.

**Architecture:** Treat this as a release-control-plane cutover. The release
train aggregates the stacked GitOps/Airflow PRs into one `master` candidate,
adds only version, changelog, badge, quality-metric, and release-planning
metadata, and keeps runtime connector behavior unchanged.

## Scope

- Manifest sparse checkout path discovery and rendering.
- GitOps plan, verify, affected planning, lock verification, bundle handoff,
  policy attestation, and schema verification contracts.
- Airflow runner pack, release policy schemas, runtime profiles, run-spec
  evidence, pod contract, final XCom outcome, and outcome gate generation.
- User docs, developer docs, architecture docs, CLI reference, schemas, and
  quality metrics.

## Release Rules

1. Do not create the `v0.11.0` tag before the release train is merged into
   `master`.
2. Keep Docker-live and vendor-live gates opt-in; OSS CI remains
   credential-free.
3. Run post-merge GitHub checks on `master` before pushing the tag.
4. Push the annotated `v0.11.0` tag only after package metadata and changelog
   both resolve to `0.11.0`.

uv run ruff check .

## Release Sequence

1. Merge the green release train PR into `master`.
2. Fetch `origin/master` and confirm `pyproject.toml`, `README.md`, and
   `CHANGELOG.md` contain `0.11.0`.
3. Wait for post-merge GitHub checks on `master`.
4. Create and push the annotated tag:

```bash
git tag -a v0.11.0 -m "Release v0.11.0"
git push origin v0.11.0
```

5. Wait for the release workflow to publish the package and GitHub Release.
6. Run the PyPI resolver/install smoke for `0.11.0`.
